LAN/WAN Network with Static Routing

Two-Site Network Design & Configuration — Cisco Packet Tracer

Project Overview

Completed

Tools & Concepts: Cisco Packet Tracer, Cisco IOS CLI, Static Routing, Subnetting, TCP/IP Model, Layer 2 Switching vs. Layer 3 Routing

I designed and configured a two-site network in Cisco Packet Tracer to get real hands-on practice with core LAN/WAN concepts instead of just reading about them. The setup is two separate local area networks — 192.168.1.0/24 and 192.168.2.0/24 — each with a switch and three end devices, connected across a simulated WAN link between two routers over a point-to-point serial connection addressed as a /30 (10.0.0.0/30).

Topology

LAN 1 (Switch0 + PC0–PC2) connects to Router0's LAN interface, and LAN 2 (Switch1 + PC3–PC5) connects to Router1's LAN interface. The two routers are joined by a serial WAN link — Packet Tracer's stand-in for a long-haul leased line — with Router0 acting as the DCE (clocking) end and Router1 as the DTE end.

1. Full topology — two LANs joined by a serial WAN link

IP Addressing Plan

I wrote out the full addressing plan before touching any configuration — this is exactly what I'd hand to a network tech, and it's what I actually referenced while configuring each device.

  • LAN 1 (192.168.1.0/24): PC0 .10, PC1 .11, PC2 .12 — gateway 192.168.1.1 (Router0's Gig0/0)
  • LAN 2 (192.168.2.0/24): PC3 .10, PC4 .11, PC5 .12 — gateway 192.168.2.1 (Router1's Gig0/0)
  • WAN link (10.0.0.0/30): Router0's Se0/0/0 at 10.0.0.1, Router1's Se0/0/0 at 10.0.0.2
  • I used a /30 on the WAN link on purpose rather than a /24 — a point-to-point link between exactly two routers only needs 2 usable addresses, so a /30 (4 addresses, 2 usable) is the non-wasteful choice for that link.

Router Configuration

Each router needed an IP address on its LAN-facing interface, an IP address on its WAN-facing serial interface, and a static route telling it how to reach the subnet it isn't directly connected to. On Router0, that meant ip route 192.168.2.0 255.255.255.0 10.0.0.2 — "for anything in the 192.168.2.0/24 network, send it to Router1's WAN interface and let Router1 handle it from there." Router1 got the mirror-image route back to 192.168.1.0/24. Neither router needs to know the other's LAN topology in detail — just the next hop to get traffic pointed the right direction.

Verifying It Actually Works

Configuring it is one thing — proving it works end-to-end is the part that actually matters. I checked interface status and routing tables on both routers, then tested real traffic crossing the WAN link.

2. Router0 — show ip interface brief, all interfaces up/up

3. Router1 — show ip interface brief, all interfaces up/up

4. Router0 — show ip route, static route to 192.168.2.0/24

5. Router1 — show ip route, static route to 192.168.1.0/24

  • Both routers show every configured interface as up/up — confirmation that no interface was left administratively shut down and no serial clocking issue was silently killing the line.
  • Both routing tables show a directly connected network (marked C) for their own LAN and a static route (marked S) for the far-side LAN — proof the static routing configuration actually took.

Cross-WAN Ping & Traceroute

The real proof is traffic actually crossing the WAN link. I pinged PC3 (192.168.2.10) from PC0, which forces the packet through the entire chain: PC0 → its gateway (Router0) → across the WAN link → Router1 → PC3's LAN → PC3, then all the way back for the reply.

6. Ping from PC0 to 192.168.2.10 — 4 sent, 4 received, 0 lost

7. Tracert showing the hop-by-hop path: PC0 → Router0 → Router1 → PC3

The traceroute is the more interesting artifact of the two — it makes the abstract idea of "routing" concrete by actually showing each hop the packet takes: local gateway, then the far router, then the destination.

What I Actually Learned

  • Switching vs. routing is the whole ballgame: Devices on the same LAN talk directly at Layer 2 through the switch using MAC addresses — no router involved at all. It's only when traffic needs to leave the local subnet that a router (Layer 3, IP addresses) gets involved, and that distinction is really the core of the entire project.
  • A router's interfaces are shut down by default: Every interface needs an explicit no shutdown before it'll pass traffic — a router with a fully correct IP address and route still won't work if you forget this one line.
  • Serial WAN links need explicit clocking: One end of a point-to-point serial link has to act as DCE and provide a clock rate; the other syncs to it as DTE. Get this wrong — set it on both ends, or neither — and the line protocol stays down even though everything else looks correctly configured.
  • Each router only needs to know its own next hop: Router0 doesn't need to understand Router1's entire LAN — it just needs one static route saying "traffic for 192.168.2.0/24 goes to 10.0.0.2" and trusts Router1 to handle it from there. That's a much smaller mental model than I expected going in.
